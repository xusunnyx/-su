# 设计决策记录（Design Notes）

本文档记录系统中各项关键设计选择的依据、替代方案与代价分析。

---

## 0. 业务抽象：数据模型设计

```text
Tenant（代理商）
  ├─1:N─ Customer（广告主客户）──1:1(每币种)── Account（预付余额）
  ├─1:N─ Order（广告订单）─────1:N────────── LedgerEntry（复式分录）
  ├─1:N─ IdempotencyRecord（幂等键）
  ├─1:N─ OutboxEvent（待投递事件）
  └─1:N─ DailyReport（按天物化聚合）
```

数据模型设计遵循"单表职责单一"原则：

- `Order` 仅描述交易意图与状态，不存储余额；
- `Account` 仅存储"当前余额"这一派生值，其真值来源于 `LedgerEntry`；
- `OutboxEvent` 仅描述"发生了什么"，不关心消费者身份；
- `DailyReport` 为查询加速而设的物化视图，可随时从 `Order` 重算得出。

这一"真值 vs 派生值"的分界线，决定了系统是否具备可对账、可重放、可更换存储的能力。

## 1. 多租户隔离：两套策略

### 方案对比

| 维度    | 行级隔离（共享库）                | 独立库/schema        |
| ----- | ------------------------ | ----------------- |
| 成本    | 低（一套库、一套迁移）              | 高（N 套库、迁移需执行 N 次） |
| 隔离强度  | 依赖代码正确性（遗漏 where 条件即串数据） | 物理隔离，连接错误库亦无法读取数据 |
| 跨租户统计 | 一条 SQL                   | 需聚合 N 个库（通常进入数仓）  |
| 大客户定制 | 困难（改表影响所有租户）             | 容易（独立升级、独立备份）     |
| 连接数   | 稳定                       | 租户数 × 连接池，易耗尽     |
| 典型场景  | 中小客户、SaaS 标准版            | 大客户、合规要求、数据驻留     |

### 本系统实现

```python
# app/db.py
Database.engine_for(tenant)          # 决定使用哪个 Engine
├─ row    → 永远使用 control engine
└─ schema → 每租户一个库文件/库名
```

行级隔离采用三层防御机制：

1. `do_orm_execute` 事件：任何 SELECT 自动追加 `tenant_id = ?` 过滤条件。业务代码仅需编写 `select(Order)`，不存在"遗漏 where 条件"的可能。
2. `before_flush` 事件：若新对象的 `tenant_id` 与当前上下文不一致，直接抛出异常。用于防御"查询 A 租户而写入 B 租户"的越权行为。
3. 租户身份来源于 `X-API-Key`，不接受请求参数中的 `tenant_id`。缺少此条，前两层防御均可被越权请求绕过。

> 为何不使用 `session.get()`？该方法可能直接命中身份映射，绕过 ORM 过滤器。
> 测试 `test_orm_filters_automatically` 即用于守护这一边界。

### 代价

- 自动过滤对 `UPDATE/DELETE` 不生效（`is_select` 判断），因此更新语句必须显式携带条件。本系统采用"先按 id 查出对象（已被过滤）→ 再按 id 更新"的方式规避。
- `with_loader_criteria` 的 lambda 闭包会被纳入查询缓存 key，租户数较多时需关注缓存命中率。

## 2. 幂等：唯一索引作为并发裁决

### 事务时序

```text
BEGIN
  INSERT idempotency_record(tenant_id, key, hash, IN_PROGRESS)   ← 唯一索引拦截并发
  ── 业务写入：订单 + 分录 + outbox ──
  UPDATE idempotency_record SET COMPLETED, response=...
COMMIT
```

### 失败场景矩阵

| 场景            | 现象               | 处理                                                              |
| ------------- | ---------------- | --------------------------------------------------------------- |
| 客户端超时重试（同键同体） | 记录已是 COMPLETED   | 返回 `200/201` + `X-Idempotent-Replay: true`                      |
| 同键不同请求体       | 指纹不一致            | `409 IDEMPOTENCY_KEY_REUSED`（客户端错误，不应静默覆盖）                      |
| 两个请求同时到达      | 后到的 INSERT 撞唯一索引 | 事务回滚 → 重试一次 → 读取胜出者结果并重放                                        |
| 处理中进程崩溃       | 记录停在 IN_PROGRESS | TTL 到期后可复用；未到期时返回 `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After` |
| 记录过期后再使用同键    | 视为新请求            | 业务侧以订单号唯一约束 + 状态机兜底                                             |

### 为何不采用分布式锁

锁解决的是"禁止并发执行"的问题，唯一索引解决的是"即使发生并发也不产生脏数据"的问题。锁存在过期、脑裂、续期等失效窗口；而数据库唯一约束无失效窗口，是正确性的最终裁决者。因此锁仅可作为性能优化手段（减少无谓重试），不能作为正确性保证。

### 代价

- 幂等表与业务表必须同库同事务；跨库场景需引入 Saga 或两阶段提交。
- 响应体需序列化存储（本系统采用 JSON 列 + 自定义 serializer 处理 datetime）。
- 存储成本：24h × 请求量，需定期清理。

## 3. 资金一致性

### 3.1 金额表示

- 对外接口采用 `Decimal`，落库采用 `BigInteger` 表示最小货币单位（USD 分、JPY 元）。
- 精度超出币种小数位直接拒绝（`10.001 USD` → 422），不做静默四舍五入。
- 严禁使用 `float`：`0.1 + 0.2 != 0.3` 在账务系统中即产生一分钱的差异。

### 3.2 扣款：条件更新（CAS）

```sql
UPDATE accounts
   SET balance_minor = balance_minor - :amount, version = version + 1
 WHERE customer_id = :cid AND currency = :cur AND balance_minor >= :amount
```

- `rowcount == 0` 即表示余额不足，无需"先查询再判断"。
- 并发下不可能扣成负数，亦无需悲观锁。
- `version` 字段可用于乐观锁冲突检测。

### 3.3 状态迁移同样采用 CAS

```sql
UPDATE orders SET status='PAID', paid_at=:now
 WHERE id = :id AND status = 'PENDING_PAYMENT'
```

两个并发的支付请求中，仅一个 `rowcount == 1`；另一个返回 409。
这一机制比"先 SELECT 判断状态、再 UPDATE"更为可靠——后者存在 check-then-act 竞态。

### 3.4 复式记账

| 业务  | 借           | 贷             |
| --- | ----------- | ------------- |
| 充值  | CASH（平台银行户） | PREPAID（客户预付） |
| 支付  | PREPAID     | REVENUE（平台收入） |
| 退款  | REVENUE     | PREPAID       |

不变式：任何一笔交易，借方合计必须等于贷方合计。
`GET /customers/{id}/account` 同时返回"存储余额"与"分录重算余额"，二者不一致即视为缺陷。

### 3.5 事务边界

下单/支付/退款流程中，"订单状态 + 余额 + 分录 + Outbox 事件"位于同一事务。缺少任一项，均会导致"钱已扣而账未记"或"账已记而钱未扣"的不一致状态。

## 4. 缓存：三种失效方式的权衡

| 方式   | 做法                        | 优点           | 缺点                       |
| ---- | ------------------------- | ------------ | ------------------------ |
| TTL  | `SETEX key ttl`           | 最简单          | 在 TTL 窗口内存在最长不一致         |
| 写后删除 | 更新 DB 后 `DEL key`         | 实时性好         | 并发下可能删除刚写入的新值；删除失败即产生脏数据 |
| 版本号  | key 中携带 `v{n}`，写路径 `INCR` | 无竞态、无需扫描 key | 旧 key 需等待 TTL 自然过期（占用内存） |

本系统采用版本号方案：支付成功后 `INCR stats:ver:{tenant}`，新的统计请求自然落到 `stats:summary:{tenant}:v2:7`，旧 key 自行过期。该方案无需 `SCAN`、无删除竞态，代价为短时间内的内存冗余。

### 缓存三大经典问题

| 问题                   | 本系统的处理                          |
| -------------------- | ------------------------------- |
| 击穿（热点 key 过期瞬间打爆数据库） | 单飞：抢到锁的请求回源，其他请求短暂等待后读取缓存       |
| 穿透（查询不存在的数据）         | 交易接口不缓存；统计接口的聚合结果天然非空           |
| 雪崩（大批 key 同时过期）      | key 中的版本号使失效由"时间驱动"转为"写驱动"，天然错峰 |

### 实时看板为何不共用同一套缓存

报表要求准确性（可容忍数十毫秒延迟），看板要求低延迟（可容忍数秒延迟）。因此 `/stats/realtime` 采用写路径 `INCRBY` + 读路径 O(1) 的模式，并通过 `source: counter | db_fallback` 明确告知调用方数据来源——缓存不可用时回源数据库，而非返回 0。

## 5. 异步解耦：Outbox 模式

| 方案                | 一致性         | 额外依赖           | 适用场景       |
| ----------------- | ----------- | -------------- | ---------- |
| `BackgroundTasks` | 弱：进程崩溃即丢失   | 无              | 通知发送、日志写入  |
| Celery + Broker   | 中：任务可能丢失/重复 | Redis/RabbitMQ | 可重试的离线任务   |
| **Outbox**        | 强：与业务同事务    | 仅需数据库          | 资金、订单、账务事件 |

Outbox 的关键设计：

1. 事件与业务同事务写入，不存在"库写成功、事件丢失"的情况。
2. Worker 至少一次投递，失败退避重试，超过次数进入 FAILED（可告警）。
3. 消费者通过重算而非累加处理：`rebuild_daily_report()` 按订单重新聚合，重投 10 次结果一致。这是"幂等消费者"最简单可靠的实现方式。
4. 切换至 Celery/Kafka 时，仅需替换 `dispatch_pending()` 的驱动，业务代码保持不变。

## 6. 限流：ZSET 滑动窗口

| 算法           | 突发容忍        | 精度  | 存储              |
| ------------ | ----------- | --- | --------------- |
| 固定窗口计数       | 边界处允许 2 倍突发 | 低   | 1 个整数           |
| 滑动窗口日志（ZSET） | 精确          | 高   | 每请求一条记录         |
| 滑动窗口计数       | 近似          | 中   | 2 个整数           |
| 令牌桶          | 允许受控突发      | 高   | 1 个 token + 时间戳 |

本系统采用 ZSET 方案以实现精确判定：

```text
ZREMRANGEBYSCORE key 0 now-window    # 清除窗口外记录
ZADD key now member                  # 记录本次请求
ZCARD key                            # 窗口内请求数
```

Redis pipeline 保证三步原子执行；超限时将刚加入的 member 删除。
无 Redis 时采用内存时间戳列表实现相同语义，接口保持不变。

代价：每个请求对应一条 ZSET 记录，内存占用与 QPS 成正比；超大规模场景需切换至令牌桶或滑动窗口计数。

## 7. 错误码与可观测性

- 所有业务错误通过 `AppError(status, code, message, details)` 返回，响应体固定为四段：`code / message / details / request_id`。前端按 `code` 分支处理，无需解析文案。
- `X-Request-Id` 贯穿日志与响应，排查时通过一条 rid 串联全链路。
- 访问日志仅记录 method/path/status/耗时/租户，不记录请求体（其中包含密钥与金额）。

## 8. 流量扩容路径

若系统负载增长 100 倍，建议按以下顺序演进：

1. **测量先行**：通过压测定位瓶颈，避免主观判断（预计首要瓶颈为 SQLite 写锁与单进程 Worker）。
2. **存储**：SQLite → PostgreSQL；按 `tenant_id` 分库分表；报表进入列存/数仓。
3. **读路径**：缓存分层（本地 + Redis）、游标分页、物化视图、读写分离。
4. **写路径**：幂等表按月分区；余额扣减针对热点账户拆分（子账户 + 汇总）。
5. **异步**：Worker 拆分为独立进程 + 分区消费 + 死信队列 + 积压告警。
6. **治理**：租户级配额、熔断降级、灰度发布。
